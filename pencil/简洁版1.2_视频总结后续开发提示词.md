# 简洁版 1.2 视频总结后续开发提示词

这份提示词只用于“视频总结”模块在阶段 0 和阶段 1 已完成之后的后续开发。

它的核心前提只有一个：

`1.2 processing`、`1.3 Aggregated Draft`、`1.4 Final Summary Chat` 不是 3 个独立页面，而是同一个屏幕在不同状态下的动态变化。

也就是说，后续 AI 不应该把 1.2、1.3、1.4 分别实现成 3 个新的独立路由页，而应该在已经完成的“视频总结入口页”基础上，围绕同一个视频总结工作区或同一个会话屏幕做状态流转。

---

## 一、你要先理解的交互前提

在 `pencil/简洁版1.2.pen` 中，视频总结流程应按下面方式理解：

1. 用户先看到 `1.1 Open A New Session`。
2. 用户点击“开始生成初稿”后，不是跳到一个全新的页面，而是当前屏幕进入 `1.2 processing` 状态。
3. 在 `1.2` 状态中，原本地上传的浅蓝色卡片需要继续保留，只是卡片中的信息更新为处理中信息。
4. 用户点击这张处理中卡片后，可以展开更详细的处理信息区块。
5. 当处理完成后，同一个屏幕继续切换为 `1.3 Aggregated Draft` 状态。
6. 用户点击“生成最终稿”后，同一个屏幕再切换为 `1.4 Final Summary Chat` 状态。

所以正确实现不是“多页面串联”，而是：

- 以一个主屏幕承载视频总结流程
- 用状态驱动 UI 切换
- 把稳定不变的区域抽成组件
- 把会变化的区域做成分阶段内容块

## 二、这次让 AI 开发时的总目标

你现在要在 Flutter 项目里继续完成“视频总结”模块，但只做 `1.2`、`1.3`、`1.4` 对应的后续开发。

注意：

- 阶段 0 和阶段 1 已经完成，不要重做。
- 这次不处理知识库模块。
- 这次不需要真实后端 API。
- 这次应当考虑组件化实现。
- 这次应当通过本地 mock service / fake repository / fake use case 的方式模拟后端给前端提供数据。

## 四、建议 AI 采用的实现思路

这部分不是让 AI 原样输出，而是你希望它遵循的实现方向。

### 1. 页面结构

建议 AI 把视频总结后续流程实现为一个统一页面，例如：

- `VideoSummaryWorkspacePage`
- 或 `VideoSummarySessionPage`
- 或在现有阶段 1 页面基础上升级为状态化页面

这个页面内部根据状态切换展示不同内容，而不是通过 3 个大页面跳来跳去。

### 2. 状态拆分

建议 AI 至少区分这些状态：

- `idle` 或 `readyToStart`
- `processing`
- `processingExpanded`
- `draftReady`
- `finalChatReady`

如果它认为更合适，也可以拆成：

- 流程主状态：`processing` / `draft` / `finalChat`
- 局部 UI 状态：如 `isProcessingDetailExpanded`

### 3. 推荐抽取的组件

建议 AI 以组件化方式开发，优先抽这些真正稳定的 UI 单元：

- 视频信息主卡片
- 处理中摘要卡片
- 处理详情展开卡片
- 聚合草稿卡片
- 总结指导输入区
- 时间戳切换条
- 系统消息块
- 用户消息块
- 聊天输入区
- 消息操作按钮组

### 4. 推荐模拟数据的方式

因为没有真实 API，建议 AI 新增少量本地模拟能力，例如：

- `startDraftGeneration()`
- `fetchProcessingSnapshot()`
- `fetchDraftResult()`
- `generateFinalSummary()`
- `sendSummaryChatMessage(String message)`

这些函数不需要接网络，只需要通过本地延时、固定数据、状态变更，模拟后端给前端返回数据即可。

### 5. 推荐模拟的数据内容

建议至少模拟这些数据：

- 视频标题
- 视频时长
- 上传来源或本地文件名
- 当前处理阶段文案
- 处理进度百分比
- 若干详细处理步骤
- 聚合草稿正文
- 总结指导语
- 最终总结主内容
- 时间戳片段数据
- 聊天消息列表
- 用户追问后的假回复

## 五、子阶段 A：先把 1.2 做成“同屏 processing 状态”

这一阶段只做 `1.2 processing` 对应状态，不做 `1.3` 和 `1.4` 的完整实现。

- 让阶段 1 的页面在点击“开始生成初稿”后，不跳新页面，而是在当前工作区切换为 processing 状态

- 卡片内容更新为处理中信息
- 支持点击展开详细处理卡片
- 用本地 mock 数据驱动进度与详情

### 不要做的事

- 不要完整实现聚合草稿界面
- 不要实现最终聊天界面
- 不要引入真实异步接口

### 可直接发给 AI 的提示词

```text
基于已经完成的阶段 0 和阶段 1，请继续开发视频总结模块，但这次只实现“子阶段 A：同屏 processing 状态”。

关键要求：

1. 不要把 `1.2 processing` 做成新的独立页面路由。
2. 你要在现有视频总结页面或统一工作区页面内部，用状态切换把界面变成 `1.2 processing` 的样子。
3. 原本上传视频的浅蓝色主卡片必须保留，只是把卡片内容改成处理中信息。
4. 用户点击这张卡片后，可以展开更详细的处理信息卡片或详情区域。
5. 需要使用本地 mock service / fake repository / 假数据函数来模拟：
   - 开始生成初稿
   - 进度变化
   - 当前处理步骤
   - 处理详情列表

实现建议：

- 采用组件化开发
- 不要把所有处理状态逻辑都塞进一个超长 widget
- 如果项目里已有状态管理方案就复用；如果没有，就用当前项目里最小可维护的方式实现

严格禁止：

- 不要直接做 1.3 和 1.4 的完整 UI
- 不要接后端 API
- 不要新建一套复杂架构

完成标准：

- 点击“开始生成初稿”后，当前屏幕能进入 processing 状态
- 浅蓝色卡片仍在原有视觉位置承担主信息

输出时请说明：

- 你新增了哪些状态或组件
```

## 六、子阶段 B：在同一屏幕切换到 1.3 聚合草稿状态

这一阶段只在 processing 基础上，继续把同一个屏幕切换到 `1.3 Aggregated Draft` 状态。

### 目标

- 当 processing 完成后，不跳新页面，而是在当前屏幕切换成草稿状态
- 展示聚合草稿主卡片和总结指导区
- 保留必要的共用页面骨架
- 为进入最终稿聊天状态做准备

### 不要做的事

- 不要完整做 1.4 聊天能力
- 不要引入真实 AI 草稿生成接口

### 可直接发给 AI 的提示词

```text
基于已经完成的 processing 状态实现，请继续开发“子阶段 B：同屏切换到 1.3 聚合草稿状态”。

关键要求：

1. 不要新增独立的 `1.3` 页面路由。
2. 当 processing 完成后，同一个视频总结工作区页面应切换为 `1.3 Aggregated Draft` 对应的 UI 状态。
3. 保持与前一状态共用的页面骨架和视觉语言，不要重新造一页完全无关的布局。
4. 草稿内容必须来自本地 mock 数据函数，而不是写死在 widget 里。
5. 页面里应包含：
   - 草稿概览或草稿主卡片

- 不要直接把 1.4 聊天系统一并做完
- 不要接真实模型生成
- 不要引入云端存储或数据库

完成标准：

- 同一屏幕可以从 processing 状态切到 draft 状态
- 草稿内容与总结指导区结构合理
- “生成最终稿”按钮具备进入下一状态的最小衔接
- 数据来自本地模拟层

输出时请说明：

- draft 状态新增了哪些组件
- 草稿数据如何 mock
```

## 七、子阶段 C：在同一屏幕切换到 1.4 最终总结聊天状态

这一阶段只做同屏进入 `1.4 Final Summary Chat` 的能力。

### 不要做的事

- 不接真实大模型
- 不做流式网络请求
- 不做语音、分享、导出等真能力

### 可直接发给 AI 的提示词

```text
基于已经完成的 draft 状态实现，请继续开发“子阶段 C：同屏切换到 1.4 最终总结聊天状态”。

1. 不要新增独立的 `1.4 Final Summary Chat` 页面路由。

输出时请说明：
```
